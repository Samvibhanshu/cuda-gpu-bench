# cuda-gpu-bench

Hand-written CUDA kernels, benchmarked and analysed the way a GPU performance engineer
would: *where is the time going, and is this kernel limited by compute, memory, or
synchronization?*

| Experiment | Kernels | Question it answers | Metric |
|---|---|---|---|
| Vector add | `vec_add` | What does a purely memory-bound kernel look like? | GB/s vs the device's memcpy bandwidth |
| Matrix multiply | `matmul_naive`, `matmul_tiled`, cuBLAS (optional) | How much does shared-memory tiling help? How far is a hand-written kernel from a tuned library? | GFLOP/s |
| Sum reduction | `reduce_atomic`, `reduce_shared`, `reduce_warp` | What does synchronization cost? Atomics vs shared-memory tree vs warp shuffles | GB/s |
| PyTorch | small transformer under `torch.profiler` | Which ops dominate, and why? FP32 vs TF32 vs FP16 | ms, TFLOP/s, Chrome trace |

## Run it

```bash
# 1. No GPU needed: unit-test the kernel logic on the CPU (g++ >= 11)
make emulate            # also: make emulate-asan   make emulate-tsan

# 2. On a machine with an NVIDIA GPU and the CUDA toolkit
make run                # builds ./bench, verifies every kernel, benchmarks, writes results/results.csv
make cublas && ./bench_cublas     # adds a cuBLAS baseline for matmul
python3 tools/summarize_results.py results/results.csv

# 3. PyTorch profiling (any machine; GPU recommended)
pip install torch
python python/profile_pytorch.py --train --peak-tflops <fp32 TFLOP/s> --peak-gbps <GB/s>
#    then open results/pytorch_trace.json in https://ui.perfetto.dev
```

`./bench` first verifies every kernel against a CPU reference (including sizes that are not
multiples of the tile) and refuses to benchmark a kernel that is wrong.
If `-arch=native` is rejected (CUDA older than 11.6): `make ARCH=sm_75` (T4), `sm_80` (A100),
`sm_86` (RTX 30xx), `sm_89` (RTX 40xx).

Free GPUs for the first run: Google Colab (T4) or Kaggle notebooks.

## What to expect, and how to explain it

These are the qualitative effects to look for. Measure them; do not quote numbers you did
not measure.

**Vector add is memory-bound.** One add per 12 bytes moved. Throughput is set by DRAM
bandwidth, so the right yardstick is GB/s compared with `cudaMemcpy` device-to-device. A
good result is a large fraction of that figure. More arithmetic cannot make it faster.

**Tiling attacks memory traffic.** In `matmul_naive` every thread streams a full row of A
and column of B from global memory: 2K loads for K multiply-adds. In `matmul_tiled` a block
loads each tile once into shared memory and every element is then reused `TILE` (16) times,
cutting global loads by about 16x in theory (caches blur this a little). Expect tiled > naive, and cuBLAS well above both
because it adds register tiling, vectorized loads, double buffering and Tensor Cores.

**Matmul is compute-bound at large N.** Arithmetic intensity is about N/6 FLOP per byte for
fp32, so it grows with N. Small N is limited by launch overhead and low occupancy instead.

**Reductions are mostly memory-bound too.** All three kernels must stream the whole input
once, so at large n they may land close together near the bandwidth ceiling; the extra
cost of contended atomics shows up more clearly at smaller n or larger grids. Report what
you see. If they are not different, that is itself the finding: say why.

## Reading the PTX

PTX is NVIDIA's virtual GPU assembly: the format `nvcc` emits and the driver compiles to
real machine code (SASS). `tools/ptx_summary.py` counts the instructions that matter. This
is the output for the kernels here, **compiled by clang** (`ptx/kernels_sm80.clang.ptx`);
`make ptx` produces nvcc's version, which will differ in details such as unrolling.

```
kernel                 ld.global ld.shared st.shared st.global       fma  bar.sync      shfl      atom
vec_add                        2         0         0         1         0         0         0         0
matmul_naive                   6         0         0         1         3         0         0         0
matmul_tiled                   2        32         2         1        16         2         0         0
reduce_atomic<...>             1         0         0         0         0         0         0         1
reduce_shared<...>             1        17         9         0         0         9         0         1
reduce_warp<...>               1         1         1         0         0         1        10         1
```

What it shows:

* `matmul_naive`: the loop body (unrolled by clang) pairs **two global loads with every
  FMA**, and the loads are `ld.global.nc`, the read-only cache path enabled by
  `const ... __restrict__`.
* `matmul_tiled`: the 16-iteration inner loop is fully unrolled, 16 FMAs fed by
  `ld.shared`, with exactly **2 `bar.sync`** per tile (load barrier, reuse barrier) and only
  2 global loads per tile.
* `reduce_shared` needs **9 barriers** (1 + log2(256) = 8 tree levels); `reduce_warp` needs
  **1 barrier + 10 `shfl.sync`** (5 per stage); `reduce_atomic` has none but one `atom` per
  thread. That is the synchronization trade-off, visible in the instructions.

To go deeper, dump machine code and profile a real kernel:

```bash
cuobjdump -sass bench | less                    # SASS, what actually runs
ncu --set full -k matmul_tiled -c 1 ./bench --skip-verify --sizes 1024   # Nsight Compute
nsys profile -o timeline ./bench --skip-verify  # Nsight Systems timeline
```

## Design notes and limits

* The emulator runs blocks one after another, so it checks intra-block logic (indexing,
  shared-memory tiling, barriers, shuffles) but not races *between* blocks.
* Atomic float adds are not associative, so reduction results vary slightly between runs;
  verification uses a relative tolerance.
* Timing uses CUDA events with warm-up runs and averages over `--iters` launches. Results
  depend on clocks and thermals; run a few times.
* `matmul_tiled` is a classic teaching kernel, not a competitive one. Natural next steps:
  register tiling (each thread computes a 4x4 patch), vectorized `float4` loads, padding
  shared memory to avoid bank conflicts, double buffering, and Tensor Cores via WMMA.

## Interview talking points

* **Coalescing:** consecutive threads of a warp should touch consecutive addresses so a warp's
  loads merge into few memory transactions. In `matmul_naive` the B loads coalesce (consecutive
  `col`); for A, threads in the same output row read the same element, which the hardware
  broadcasts.
* **Why tiling works:** it converts redundant global loads into shared-memory reuse. Global
  traffic drops by the tile edge.
* **Why two `__syncthreads()` in the tiled loop,** and why no thread may `return` before them
  (divergent barriers deadlock or are undefined).
* **Warp = 32 threads executing in lockstep;** divergence inside a warp serializes both paths.
* **Roofline thinking:** compare achieved FLOP/s and GB/s with the hardware peaks to decide
  whether a kernel is compute-bound or memory-bound, then optimize the right resource.
* **Atomics vs hierarchical reduction:** reduce locally first (registers, warp shuffles,
  shared memory) and touch the global address once per block.
